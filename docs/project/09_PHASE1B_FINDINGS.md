- **損保最新証券突合**: 313 (`EXT-obs_損保最新証券-突合`) → 307 (`EXT-obs_内部CallPS-PAYLOAD`) → PowerShell (※ 313は 299 を経由しない)
  - DDR証拠: 313 Step 127 (`スクリプト実行 [「EXT-obs_内部CallPS-PAYLOAD」(307), 引数: $payload]`)

### 307の現行エラー系問題（静的トレース結果）
1. **一時payload書込み失敗**: 307 Line 34 `$errWrite ≠ 0` → 生ダイアログ「`BE_GetLastError = ...`」表示 → 結果指定なしの空文字 `[ ]` で終了。299 側は空結果を受け取り「`Obsidian連携エラー : `」を表示。
2. **PowerShell起動失敗 / stdout空**: 307 Line 45 `$stdout` 空 → 生ダイアログ「`出力が空です。BE_GetLastError: ... 実行コマンド: ...`」表示 → 空 `$stdout` を返送。
3. **課題**: 生エラーコードや Vault 絶対パス等の技術情報が一般利用者に露出する。また 307 起動失敗時に呼出元へ `requestId` が引き継がれない。
4. **評価**: 307 の実行層エラーに限り最小改修（構造化 JSON 返却）が必要という Phase 1A の判断（ゲート②）が裏付けられた。

### 2. BOM・改行コード実態と編集方針
* **BOM実態**: UTF-8 BOMあり 8件 / UTF-8 BOMなし 258件。
* **改行コード実態**: LF 254件 / CRLF 4件 / mixed 8件。
* **mixed 8件の構造と編集方針**: 8件すべて「frontmatterがLF、本文がCRLF」の構造。本文非改変原則に従い、frontmatter のみ LF で編集し、本文の CRLF には一切変更を加えない。
* **新規ファイル方針**: UTF-8 BOMなし、改行コード LF。

### 3. 全6 noteTypeの一意性と重複保護
* **業務仕様の確定**: 契約一覧/事故一覧/契約/事故/決算書/その他の全6種は「同一顧客内に各1ノート」を業務仕様として確定。安全条件を満たす場合のみ条件付き自動作成候補とする。
* **Vault実態での重複検出**: 調査により **4顧客で同一noteType重複が存在**（事故1顧客、契約3顧客）することを確認。
* **重複保護方針**: 候補が複数存在するケースでは、自動統合や選択を行わず `DUPLICATE_NOTE_TYPE`（UUID重複時は `DUPLICATE_UUID`）で警告を表示し処理を安全に中止する。

### 4. 境界規則と tags 形式
* **frontmatter境界**: ファイル第1行の内容が厳密に `---` と一致する場合のみ開始境界とし、第2行以降で最初に現れる単独行 `---` を終了境界とする（本文中の後続 `---` は境界として扱わない。本文中 `---` 存在 257件）。
* **tags形式**: ブロック配列 (`- item`) 257件、`tags:` 直後に値がなく次の同階層キーまたはfrontmatter終了へ移る形式 9件。**この値なし形式に限り**既存tags空集合として扱い `INVALID_YAML` にしない。ただし `tags: null` / `tags: ""` / `tags: 0` / `tags: {}` はこれと同一扱いにせず、未対応または不正型候補とする（適用条件を混同しないこと）。

## 7. Phase 1B-2 SYNC_NOTE transport設計調査 (2026-07-25)

### 1. FileMaker Pro 19.6.3 JSON関数の実機確認結果
*   JSONString = 1, JSONNumber = 2, JSONObject = 3, JSONArray = 4, JSONNull = 6。
*   JSONGetElementの戻り値だけでは数値1と文字列"1"を区別できない。型判別には `JSONGetElementType` が必須。
*   構文不正時は `?` で始まるエラー文字列が返るため、`Left(type;1) = "?"` 等での事前検証が必要。

### 2. Base Elements Plug-In 5.0.0.2 実機確認結果
*   `Write-Host` の出力は `BE_ExecuteSystemCommand` の戻り値へ混入する。
*   正常実行時の `BE_GetLastError` は 0。
*   これにより、stdout非空かつBEエラー非0 の場合は、stdoutを成功responseとして採用してはならない。

### 3. SYNC_NOTE transport 分割方針と責務
*   既存307 (`EXT-obs_内部CallPS-PAYLOAD`) はMODE系専用として維持する。
*   新規 `EXT-obs_内部CallPS-SYNC-NOTE` を作成し、JSON response固定とする。
*   transport層は `VaultRoot` と `requestId` のみを抽出・参照し、他は素通しする。
*   transportエラー時はJSON固定応答を生成し、一般利用者向けの `userMessage` のみを返す（BEエラー等の技術情報は隠蔽）。

### 4. PowerShell 構成方針
*   既存 `FM-Obsidian-Bridge-Payload.ps1` へ早期分岐を追加する。
*   専用のps1に分割しない（既存の会社名正規化等の重複を避けるため）。
*   SYNC_NOTE経路では `Write-Host` や PIPE response (`Out-OK` 等) は禁止され、最終JSON response 1件のみをstdoutへ出力する。
